# レビュー要件

## 概要

本ドキュメントは「この数字、なんの数字？」クイズアプリケーションの PR レビューにおけるレビュー要件を定義する。
プロジェクトの開発プロセス（GitHub Flow、Issue 4 カテゴリ管理）および技術スタックに基づき、品質を担保するためのチェック観点を体系化する。

---

## 判定方式について

各チェック項目には「判定」列を設け、判定方式を明示する。

| 判定 | 意味 | 説明 |
|---|---|---|
| 🤖 AI | AI 自動判定 | 構造的・機械的に判定可能な項目。AI（GitHub Copilot 等）が自動でチェックし、合否を判定する |
| 👤 人間 | 人間レビュー必須 | 意味的整合性・主観的判断・視覚的確認が必要な項目。AI は分析結果の提示や問題の疑いがある箇所の指摘までを行い、**最終判定は必ず人間のレビュアーが行う** |

### AI と人間の役割分担

- **AI の役割**: 🤖 AI 項目は自動で合否判定する。👤 人間 項目については、関連する差分・情報の抽出と分析結果の提示を行い、人間の判断を支援する
- **人間レビュアーの役割**: 👤 人間 項目について最終的な合否を判定する。AI が提示した分析結果を参考に、ドメイン知識・設計意図・ユーザー体験の観点から判断する
- **PR の Approve 条件**: すべての 🤖 AI 項目がパスし、かつ、すべての 👤 人間 項目について人間レビュアーが OK を出していること

## 全 PR 共通チェック項目

| # | 観点 | 確認内容 | 判定 |
|---|---|---|---|
| C-1 | ブランチ命名 | `feature/#<issue番号>-<短い説明>` の命名規則に準拠しているか | 🤖 AI |
| C-2 | Issue 参照 | PR 本文に `Closes #<issue番号>` で対応する issue を参照しているか | 🤖 AI |
| C-3 | PR 記載事項 | 変更の概要、対応 issue 番号、テスト結果の概要が記載されているか | 🤖 AI |
| C-4 | 作業開始条件 | 親ユーザーストーリーに「確認済み」ラベルが付与された状態で作業されているか | 🤖 AI |
| C-5 | CI パス | GitHub Actions の CI ワークフロー（Unit / Integration / System Test）がすべてパスしているか | 🤖 AI |
| C-6 | 差分の妥当性 | 対応 issue のスコープ外の変更が含まれていないか | 👤 人間 |
| C-7 | インデント | 4文字インデントになっているか | 🤖 AI |

> **C-6 が人間レビュー必須である理由**: 変更差分が issue のスコープ内かどうかは、issue の意図・背景の理解に基づく意味的判断が必要であり、AI による機械的な判定では見落としや誤判定のリスクがある。AI は差分の一覧と issue 内容の対比を提示し、人間が最終判断する。

## 設計（design ラベル）PR のレビュー観点

| # | 観点 | 確認内容 | 判定 |
|---|---|---|---|
| D-1 | 配置場所 | 要件定義は `docs/specs/`、基本設計・アーキテクチャは `docs/design/` に配置されているか | 🤖 AI |
| D-2 | コード例禁止 | ドキュメントにコード例（ソースコード断片）が含まれていないか | 🤖 AI |
| D-3 | AC との整合性 | 親ユーザーストーリーの Acceptance Criteria（EARS 形式）と設計内容が整合しているか | 👤 人間 |
| D-4 | 既存ドキュメントとの一貫性 | 技術スタック定義や既存の要件・設計ドキュメントと矛盾がないか | 👤 人間 |
| D-5 | 技術選定原則 | 「シンプルさ優先」「Spring Boot エコシステム活用」「テスト容易性」「ローカル完結」「最小依存」の 5 原則に反していないか | 👤 人間 |
| D-6 | 完全性 | 設計 issue に記載された変更対象ドキュメント・設計方針がすべて反映されているか | 👤 人間 |

> **D-3〜D-6 が人間レビュー必須である理由**:
> - **D-3**: EARS 形式の AC と設計内容の意味的整合は、要件の意図を正しく理解した上での判断が必要
> - **D-4**: 既存ドキュメント間の微妙な矛盾や設計思想の不一致は、ドメイン知識に基づく判断が必要
> - **D-5**: 「シンプルさ」「テスト容易性」等の抽象原則への適合は、プロジェクト文脈を踏まえた主観的判断が不可避
> - **D-6**: 設計方針の「すべてが反映されているか」という網羅性判断は、設計意図の深い理解が必要

## 実装（implementation ラベル）PR のレビュー観点

### コード品質

| # | 観点 | 確認内容 | 判定 |
|---|---|---|---|
| I-1 | Java 21 活用 | Record、Sealed Classes、Pattern Matching 等の Java 21 言語機能を適切に活用しているか。不要なボイラープレートが残っていないか | 👤 人間 |
| I-2 | Spring Boot 規約 | DI（コンストラクタインジェクション推奨）、`@Configuration`、`@Service`、`@Controller` 等の Spring Boot アノテーション規約に準拠しているか | 🤖 AI |
| I-3 | レイヤー分離 | Controller → Service → Repository / DataLoader のレイヤードアーキテクチャの責務分離が適切か。レイヤーの跨ぎ越し（Controller から Repository を直接呼ぶ等）がないか | 🤖 AI |
| I-4 | データモデル | クイズデータが Java Record + List/Map によるイミュータブルなデータモデルで表現されているか | 🤖 AI |
| I-5 | Thymeleaf テンプレート | Natural Templating として妥当か。HTML として単体プレビュー可能か | 👤 人間 |
| I-6 | フロントエンド | Bootstrap 5（CDN）利用が適切か。不要な JavaScript フレームワーク・ライブラリが追加されていないか | 🤖 AI |
| I-7 | 最小依存 | 不要な外部ライブラリが追加されていないか。Spring Boot BOM で管理可能なバージョンは BOM に委任しているか | 🤖 AI |
| I-8 | ビルド設定 | `build.gradle.kts` の変更が適切か。Kotlin DSL として型安全に記述されているか | 🤖 AI |

> **I-1, I-5 が人間レビュー必須である理由**:
> - **I-1**: Java 21 言語機能の「適切な活用」は、コードの文脈・可読性・保守性を総合的に考慮した判断が必要。AI はボイラープレートの検出や改善候補の提示を行うが、最終的な採否は人間が判断する
> - **I-5**: Natural Templating として HTML 単体でプレビュー可能かどうかは、ブラウザでの視覚的確認が必要であり、AI による静的解析だけでは判定できない

### テスト品質

| # | 観点 | 確認内容 | 判定 |
|---|---|---|---|
| T-1 | テスト計画準拠 | 実装 issue の詳細設計に記載されたテスト計画どおりのテストが実装されているか | 👤 人間 |
| T-2 | Unit Test | JUnit 5 + Mockito + AssertJ を使用し、個々のクラス・メソッド単位で検証しているか。外部依存はモック化されているか | 🤖 AI |
| T-3 | Integration Test | `@SpringBootTest` / `@WebMvcTest` + MockMvc を使用し、Controller-Service-Repository 間の結合が検証されているか。ソースセット `integrationTest` に配置されているか | 🤖 AI |
| T-4 | System Test | Playwright（Java）+ JUnit 5 で Gherkin 形式のテストケース設計に基づく E2E テストが実装されているか。ソースセット `systemTest` に配置されているか | 🤖 AI |
| T-5 | テスト独立性 | 各テストが他のテストに依存せず、単独で実行可能か。テストデータのセットアップ・クリーンアップが適切か | 🤖 AI |
| T-6 | テスト可読性 | テストメソッド名・アサーションメッセージから、テストの意図・期待結果が読み取れるか | 👤 人間 |

> **T-1, T-6 が人間レビュー必須である理由**:
> - **T-1**: 実装 issue 内の自由記述形式のテスト計画と実装されたテストの対応関係は、テスト計画の意図を理解した上での意味的照合が必要
> - **T-6**: テストの「可読性」は主観的な品質属性であり、チーム内の共通理解に基づく人間の判断が不可欠

### セキュリティ・堅牢性

| # | 観点 | 確認内容 | 判定 |
|---|---|---|---|
| S-1 | 入力バリデーション | ユーザー入力に対して Jakarta Bean Validation（Hibernate Validator）によるバリデーションが適切に適用されているか | 👤 人間 |
| S-2 | XSS 対策 | Thymeleaf の `th:text`（自動エスケープ）を使用し、`th:utext` の不用意な使用がないか | 🤖 AI |
| S-3 | エラーハンドリング | 予期しない例外に対する適切なエラーハンドリングがあるか。スタックトレースがユーザーに露出しないか | 👤 人間 |

> **S-1, S-3 が人間レビュー必須である理由**:
> - **S-1**: バリデーションアノテーションの存在は AI で検出可能だが、ビジネスルールに照らして「適切な」バリデーションルールが設定されているかはドメイン知識に基づく判断が必要
> - **S-3**: エラーハンドリングの「適切さ」は、ユーザー体験・セキュリティ・運用上のログ要件を総合的に考慮した判断が必要。AI は未処理例外のパスやスタックトレース露出の可能性を指摘するが、対処方針の妥当性は人間が判断する

## 手動テスト（manual-test ラベル）PR / Issue のレビュー観点

| # | 観点 | 確認内容 | 判定 |
|---|---|---|---|
| M-1 | Gherkin 形式 | テストケースが Gherkin 形式（Feature / Scenario / Given / When / Then）で記述されているか | 🤖 AI |
| M-2 | 自動テスト補完性 | Unit / Integration / System Test でカバーできない領域（視覚的確認、UX 等）を対象としているか | 👤 人間 |
| M-3 | テスト結果記録 | テスト実施結果（合否、スクリーンショット等）が issue に記録されているか | 👤 人間 |
| M-4 | 環境条件 | 前提条件・テスト環境（ブラウザ、OS、解像度）が明記されているか | 🤖 AI |

> **M-2, M-3 が人間レビュー必須である理由**:
> - **M-2**: 手動テストが自動テストの補完として適切な領域をカバーしているかは、自動テストのカバレッジ状況とテスト対象の性質（視覚的確認、UX 等）に対する総合的判断が必要
> - **M-3**: テスト結果の記録が十分かどうか（合否判定の妥当性、エビデンスの品質）は人間による確認が必要

## レビュープロセスルール

| # | ルール |
|---|---|
| P-1 | PR マージには**最低 1 名の人間レビュアーの承認**を必須とする |
| P-2 | CI がすべてパスしていない PR はマージしない |
| P-3 | レビュー指摘は「Must（必須修正）」と「Want（推奨・任意）」を明示する |
| P-4 | Must 指摘がすべて解消されるまで Approve しない |
| P-5 | 設計 PR は技術スタック定義の 5 原則との整合性を重点的に確認する（👤 人間判断） |
| P-6 | 実装 PR はテスト計画との整合性（T-1）を最優先で確認する（👤 人間判断） |
| P-7 | AI は 👤 人間 項目について分析結果と懸念点を提示し、人間レビュアーに判断を委ねること。AI が 👤 人間 項目の合否を最終判定してはならない |
