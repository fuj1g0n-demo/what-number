# ハイブリッド開発方針

## 概要

本ドキュメントは、エンタープライズ（金融・公共）のウォーターフォール型開発の制約下において、
アジャイルで実践されている手法・ツール・考え方を持ち込み、**開発効率と開発体験（DevEx）を向上させる**
ための開発方針を定義する。

本方針は「アジャイルへの移行」や「アジャイルの部分適用」を目的としない。
ウォーターフォールの制約（フェーズゲート、文書成果物、トレーサビリティ、承認・監査）を
満たしたまま、その内側でエンジニアリングプラクティスと自動化を最大限に活用することを目的とする。

## 適用範囲と位置づけ

- 本リポジトリはデモアプリケーションであり、本方針の**リファレンス実装**として機能する
- 本方針の各プラクティスは、実際の顧客プロジェクトへ導入する際の実証済みカタログとして参照される
- 契約形態（請負・準委任）や顧客固有の監査要件によって適用可否が変わる項目には、その旨を明記する

## 前提とする制約（ウォーターフォールの制約）

本方針が「満たすべき制約」として扱うものを以下に定義する。これらは撤廃・回避の対象ではない。

| 制約 | 内容 |
|---|---|
| フェーズゲート | 要件定義・設計・実装・テスト・リリースの各フェーズに承認関門があり、通過には成果物と承認が必要 |
| 文書成果物 | 要件定義書・設計書・テスト設計書・テスト結果報告書等の文書が契約・監査上必須 |
| トレーサビリティ | 要件からテスト結果までの追跡可能性（トレーサビリティマトリクス）が監査上要求される |
| 承認・監査証跡 | 誰が・いつ・何を承認したかの記録が必要であり、事後の監査に耐えること |
| 変更管理 | ベースライン確定後の変更は、影響分析と承認を経た変更管理プロセスに従うこと |

## 基本原則

1. **ゲートは証跡を消費する**: フェーズゲートと CI/CD は矛盾しない。CI/CD が開発の過程で継続的に
   証跡（テスト結果、カバレッジ、レビュー承認、デプロイ記録）を蓄積し、フェーズゲートは
   蓄積済みの証跡を評価・承認する場と再定義する。ゲートのために証跡を後から作らない
2. **成果物は書くのではなく生成する**: 文書成果物は、コード・テスト・issue・PR という一次情報から
   自動生成することを優先する。手書きの文書は一次情報とのドリフトが宿命であり、
   生成された文書はドリフトしない（Living Documentation）
3. **仕様は資産である**: 契約・統制上必須である事前仕様化（要件定義・設計）のコストを、
   AI エージェントの実装を駆動する資産（Spec-Driven Development）へ転換する。
   EARS 形式の要件と Gherkin 形式のテストケースはその中核である
4. **輸入するのはプラクティスであり、セレモニーではない**: デイリースクラム等の儀式の形式的導入
   （いわゆる Agile Theater）は行わない。輸入対象はエンジニアリングプラクティス・自動化・可視化に限る
5. **機械判定可能なものはすべて自動化する**: レビュー・チェックのうち構造的・機械的に判定可能な項目は
   CI とツールに委ね、人間の判断は意味的・主観的判断が必要な項目に集中させる
   （レビュー要件の 🤖 AI / 👤 人間 の判定区分はこの原則の適用である）
6. **待ち時間を可視化する**: 開発のリードタイムを「エンジニアリング時間」と「承認・手続きの待ち時間」に
   分離して計測し、ボトルネックがプロセスのどこにあるかを事実で示す
7. **開発体験（DevEx）を改善の評価軸とする**: フィードバックループの速さ、認知負荷の低さ、
   フロー状態の保ちやすさの 3 次元で施策を評価する

## 制度的裏付け

日本の金融・公共分野において、ウォーターフォール制約下でのアジャイル的手法の導入は
以下の公的文書によって裏付けられており、顧客・監査側への説明根拠として利用できる。

| 発行元 | 文書 | 発行時期 |
|---|---|---|
| IPA（情報処理推進機構） | アジャイル開発版「情報システム・モデル取引・契約書」 | 2020年3月 |
| IPA | アジャイルプロジェクト実践ガイドブック 2023年版 | 2023年7月 |
| IPA（ITSS+） | アジャイル開発の進め方 ―アジャイル領域へのスキル変換の指針― | 2024年5月 |
| 内閣官房 IT 総合戦略室（現デジタル庁所管） | アジャイル開発実践ガイドブック | 2021年3月 |
| 行政情報システム研究所（AIS） | 行政におけるアジャイル開発の実践に向けた調査研究（プロジェクト実践編・組織マネジメント編） | 2024年3月 |
| FISC（金融情報システムセンター） | 金融機関におけるアジャイル型開発の効果的な進め方と実践的な工夫・留意点（国内調査レポート） | 2026年5月 |

補足:

- 「Water-Scrum-Fall」は Forrester Research の Dave West と Tom Grant が 2011 年に提示した概念であり、
  外殻をウォーターフォール統制、内側の構築をイテレーティブに行う現実的な混合形態を指す。
  本方針はこの混合を場当たり的にではなく**意図的に設計する**立場をとる
- 継続的コンプライアンス（compliance-as-code）による監査準備工数の削減効果は業界事例で広く報告されているが、
  削減率の数値は出典により大きく異なるため、本方針では特定の数値を効果の根拠としない

## プラクティス体系

プラクティスは Agent 設計（agent-design.md）と同じ 2 側面で整理する。

### 開発プロセス系プラクティス

#### 要件とトレーサビリティ

| プラクティス | 内容 | ウォーターフォール成果物との対応 |
|---|---|---|
| EARS 形式の Acceptance Criteria | 要件を構造化された自然言語パターンで記述する（既採用）。EARS は Rolls-Royce 発の要求記述手法（2009年）であり、AWS Kiro 等の Spec-Driven Development ツールでも採用されている | 要件定義書の要求記述 |
| Gherkin 形式のテストケース | EARS の各 AC に対応する Given/When/Then のシナリオを策定する（既採用）。1 つのシナリオが「テスト設計書」と「回帰テスト」を兼ね、文書とテストの二重管理を排除する | テスト設計書 |
| Issue 階層による WBS | GitHub ネイティブ sub-issues（2025年4月 GA）でユーザーストーリーを頂点とする階層を構成する（既採用） | WBS・課題管理台帳 |
| Issue Forms による構造化 | ユーザーストーリーの issue テンプレートを構造化フォーム化し、EARS 形式の AC を必須入力フィールドとする。品質チェックの機械検証性を高める | 要件定義書の様式統一 |
| トレーサビリティマトリクス（RTM）の自動生成 | Gherkin シナリオへの issue 番号タグ付け規約を設け、issue 階層・PR リンク・テスト結果から要件〜テスト結果の対応表を自動生成する | トレーサビリティマトリクス |
| Spec-Driven Development との整合 | GitHub Spec Kit（GitHub 公式 OSS）や AWS Kiro の spec 3 点構成（要件・設計・タスク）は、本リポジトリの user-story / design / implementation の issue カテゴリ構成と同型である。仕様承認前に実装へ進まないゲートが両者に共通する | 要件定義書・基本設計書・作業指示 |

#### プロジェクト管理と可視化

| プラクティス | 内容 | ウォーターフォール成果物との対応 |
|---|---|---|
| マイルストーン = フェーズ | GitHub Milestones をウォーターフォールのフェーズに対応させ、マイルストーン完了をフェーズゲート通過の起点とする | フェーズ完了判定 |
| GitHub Projects によるフェーズ管理 | Projects のカスタムフィールドでフェーズ・ゲート状態を管理し、フェーズ別のかんばんビューで進捗を可視化する | 進捗報告書 |
| Definition of Ready / Done | フェーズ・作業の入口条件と出口条件を明文化し、可能な限り自動チェック化する。「確認済み」ラベルによる作業開始条件は Definition of Ready の実装である（既採用） | フェーズゲート判定基準 |
| フロー効率の計測 | issue・PR のタイムスタンプからリードタイムを算出し、「エンジニアリング時間」と「承認待ち時間」を分離して可視化する。DORA 指標はエンジニアリング側にのみ適用し、統制上必須の待ち時間と混同しない | 定量的プロセス報告 |
| フィーチャートグルによるデプロイとリリースの分離 | 未完成機能を無効化した状態で継続的に統合・デプロイし、リリース判定（ゲート承認）と技術的デプロイを分離する。ビッグバン統合のリスクを回避する | リリース判定 |

#### レビューと承認の統制

| プラクティス | 内容 | ウォーターフォール成果物との対応 |
|---|---|---|
| レビューチェックリストのドキュメント化 | レビュー観点を review-requirements.md として明文化し、AI 自動判定と人間判定を区分する（既採用） | レビューチェックリスト・レビュー記録 |
| 機械的チェックの CI 自動化 | ブランチ命名・issue 参照・記載事項等の機械判定可能な項目は、エージェント任せにせず CI で自動判定・自動 fail させる | レビュー記録の一部自動化 |
| PR = レビュー議事録 | PR のレビュースレッドと Approve 記録を、設計レビュー・コードレビューの議事録および承認記録として扱う。GitHub 上の承認は時刻・実施者が改竄不能な形で記録される | レビュー議事録・承認記録 |
| CODEOWNERS による責任分担 | ファイルパスとレビュー責任者の対応を宣言的に管理し、GitHub が承認を強制する | 責任分担表（RACI） |
| Protected Environments による リリース承認 | ステージング・本番環境への デプロイに指名レビュアーの承認を必須とし、承認記録を監査証跡とする（紙の承認手続きの代替） | リリース承認記録 |
| ADR（Architecture Decision Record） | 設計判断を文脈・決定・帰結の形式で記録し、docs/design/adr/ 配下で管理する。ステータス遷移（提案 → 承認 → 廃止）が設計レビュー・承認・変更管理に対応する | 設計判断記録・設計レビュー記録 |

#### 変更管理と欠陥管理

| プラクティス | 内容 | ウォーターフォール成果物との対応 |
|---|---|---|
| 変更要求の issue 管理 | ベースライン確定後（該当マイルストーン完了後）の要件・設計変更は、変更対象のユーザーストーリーを reopen するか、新たなユーザーストーリー issue として起票し、影響分析の記録をコメントとして残した上で通常のチェックフロー（確認済み判定）を通す | 変更管理台帳・影響分析書 |
| 欠陥の issue 管理 | テストフェーズ以降に発見された欠陥は `bug` ラベルの issue として起票し、原因・修正 PR・再テスト結果を issue 上に集約する。欠陥 issue は関連するユーザーストーリーに紐づける | 障害管理台帳 |
| 変更の追跡可能性 | すべての変更はブランチ・PR・issue の連鎖で追跡可能とする（GitHub Flow の運用そのものが変更管理の証跡となる） | 変更履歴 |

### Coding Agent の利活用

Coding Agent（GitHub Copilot Coding Agent、Claude Code、OpenAI Codex 等の自律型コーディングエージェント）を、
本方針の制約と原則の下で「統制された実装者」として活用する。
Coding Agent は開発効率向上の手段であると同時に、その活動のすべてが GitHub 上に記録されるため、
人間の開発者以上に完全な作業証跡を残す実装者である。

#### 位置づけの原則

1. **仕様が Agent を駆動する**: 原則 3（仕様は資産）の帰結として、確認済みのユーザーストーリー
   （EARS 形式の AC）・設計・Gherkin テストケースを Coding Agent への入力（作業指示）とする。
   仕様の品質が Agent の成果物の品質を規定するため、事前仕様化への投資がそのまま回収される
2. **人間と同一の統制に服する**: Coding Agent の成果物は人間の開発者と同一のプロセス
   （ブランチ規則・PR 必須・レビュー要件・CI ゲート）を通過する。Agent 専用の抜け道を設けない
3. **委任しても責任は移らない**: Agent への委任後も、成果物に対する責任は PR を承認した
   人間レビュアーと、委任を行った担当者にある。レビュー要件の 👤 人間 判定項目を
   AI が最終判定してはならない統制は、Coding Agent の成果物に対しても同様に適用される

#### 適用領域

| 適用領域 | 内容 | ウォーターフォール成果物との対応 |
|---|---|---|
| 実装 issue の委任 | 「確認済み」の親ユーザーストーリーに紐づく実装 issue を Agent に割り当て、ドラフト PR の作成までを委任する | 実装作業記録（issue・PR の連鎖） |
| テストコードの生成 | Gherkin テストケースからの自動テスト実装、既存コードへのテスト追補を委任する | テスト実装記録 |
| ドキュメント・証跡の生成 | トレーサビリティマトリクス、テスト結果の整理、リリースノート等の一次情報からの生成を委任する（原則 2 の実行主体） | 各種文書成果物 |
| レビュー支援 | レビュー要件の 🤖 AI 判定項目の自動実行と、👤 人間 判定項目の分析材料の提示を行わせる | レビュー記録の一部 |
| 手動テストの証跡収集 | 画面キャプチャ・操作トレースの取得と issue への記録を委任する | テスト実施証跡 |

#### 統制設計

| 統制 | 内容 |
|---|---|
| 委任の入口条件 | Definition of Ready を満たすこと。すなわち親ユーザーストーリーに「確認済み」ラベルが付与され、EARS 形式の AC と必要な設計情報が issue 上に揃っていること。仕様が不十分なまま委任しない |
| PR 経由の変更のみ | Agent は保護ブランチへ直接プッシュできず、すべての変更はドラフト PR を経由する。ブランチ保護規則は Agent に対しても完全に適用される |
| 人間承認ゲート | Agent が作成した PR の CI 実行およびマージには人間の承認を必須とする。この承認記録が「AI 成果物に対する人間の検収記録」として監査証跡になる |
| 作業ログの証跡化 | Agent の作業過程（セッションログ・実行ログ）は GitHub 上に記録され、成果物がどのように生成されたかを事後検証できる |
| スコープ統制 | Agent の変更が委任した issue のスコープ内に収まっているかは人間が判定する（レビュー要件の差分妥当性チェックを適用） |
| 知識の供給統制 | Agent へのリポジトリ固有知識は、常時ロードされる instructions と APM 管理の Agent Skill を通じて供給する（agent-design.md 参照）。個人環境限りの口頭指示に依存させず、知識の供給経路自体をバージョン管理する |
| 機密情報の統制 | Agent に参照させてはならない情報（認証情報、顧客データ等）はリポジトリに置かない原則を徹底し、組織のコンテンツ除外設定を併用する |

#### 効率と統制の両立という観点

Coding Agent の導入は、ウォーターフォール統制と衝突しない。むしろ以下の点で親和性が高い。

- Agent の全作業が issue・PR・実行ログとして自動的に記録されるため、作業証跡の完全性は
  人間の手作業よりも高い（原則 1 の証跡蓄積に寄与する）
- 委任の前提として仕様の完備が必要であるため、フェーズゲート（要件・設計の承認）を
  経ることが Agent 活用の効率をむしろ高める
- Agent が機械的作業（定型実装・テスト追補・文書生成）を担うことで、人間は
  👤 人間 判定項目（意味的整合・設計妥当性）へ集中でき、原則 5 の分業が徹底される

#### Coding Agent 特有のリスクと対策

| リスク | 内容 | 対策 |
|---|---|---|
| 過剰委任 | 仕様が曖昧なまま委任し、意図と異なる成果物に手戻りが発生する | 委任の入口条件（Definition of Ready）を厳守する。曖昧さが残る issue は先に品質チェックフローへ戻す |
| レビュー形骸化 | Agent の生成量に人間レビューが追いつかず、承認が形式化する | 機械判定可能な項目を CI で先に落とし、人間レビューの対象を絞る。1 PR のスコープを issue 単位に保つ |
| 見かけ上の正しさ | テストが通るが要件の意図とずれた実装（仕様の誤解釈）が混入する | EARS の AC と Gherkin シナリオの対応を人間が確認する（AC 整合性チェックは人間判定を維持） |
| 知識のドリフト | Agent へ供給する知識（instructions・Skill）が実態と乖離し、誤った規約で生成される | 知識の正本をドキュメントに置き、Skill は導線に徹する（ドキュメント正本主義）。APM の完全性検証を CI で行う |
| 責任の曖昧化 | 「AI が書いたから」と品質責任の所在が不明確になる | 承認した人間レビュアーが成果物に責任を負うことを運用ルールとして明記する |

## 既存プロセスとの対応

本方針は既存の統制（copilot-instructions.md、review-requirements.md、agent-design.md）と矛盾せず、
それらを本方針の「実装済み部分」として位置づける。

| 既存の統制 | 本方針上の位置づけ |
|---|---|
| Issue 4 カテゴリ（user-story / design / implementation / manual-test） | Spec-Driven Development の spec 3 点構成に対応する issue 階層 |
| 「確認済み」ラベルによる作業開始条件 | Definition of Ready の実装。プロセス完遂と証跡を根拠とする統制（agent-design.md 参照） |
| EARS + Gherkin の記述規約 | 原則 3（仕様は資産）の中核実装 |
| review-requirements.md の 🤖/👤 判定区分 | 原則 5（機械判定可能なものは自動化）の実装。ArchUnit 等の導入により 👤 から 🤖 への移行を継続的に進める |
| GitHub Flow・PR 必須・レビュー承認必須 | レビュー議事録・承認記録・変更管理の証跡基盤 |
| Agent Skill（APM 管理） | プラクティスの手順的知識を担う配布単位。新規プラクティスの導入時は対応する Skill の新設・拡張を検討する |

## 導入ロードマップ

導入は証跡価値と導入コストの比で優先順位づけする。各段階は独立して価値を持ち、
前段の完了を待たずに個別判断で着手してよい。

### 第 1 段階（高価値・低コスト）

1. アーキテクチャ適合テスト（ArchUnit）の導入と、レビュー要件該当項目の 👤 から 🤖 への判定変更
2. Gherkin シナリオへの issue 番号タグ付け規約と、トレーサビリティマトリクス自動生成
3. ADR ディレクトリ（docs/design/adr/）の新設と記録運用の開始
4. ユーザーストーリー Issue Forms の構造化（EARS 必須フィールド化）
5. 機械的レビュー項目（ブランチ命名・issue 参照等）の CI 自動判定化

### 第 2 段階（証跡の拡充）

6. テストレポート・E2E トレースの CI 成果物としての長期保存
7. ミューテーションテストの導入と品質ゲート化
8. フロー効率（エンジニアリング時間と承認待ち時間の分離）の定期計測
9. Protected Environments によるリリース承認ゲート
10. 実装 issue の Coding Agent への委任運用の開始（委任の入口条件と人間承認ゲートの運用確立）
11. フェーズゲート証跡パッケージ（マイルストーン完了時の証跡集約）の自動生成

### 第 3 段階（発展）

11. ビジュアルリグレッションテストのベースライン運用
12. SBOM・ビルド来歴・署名のリリースパイプライン組み込み
13. フィーチャートグルの運用整備
14. C4 モデルによるアーキテクチャ図の Diagrams-as-Code 化
15. 証跡・文書生成業務（トレーサビリティマトリクス、リリースノート等）の Coding Agent への委任拡大

## アンチパターンと回避策

| アンチパターン | 内容 | 本方針での回避策 |
|---|---|---|
| Agile Theater | セレモニーだけを形式導入し、実質の変化がない | 原則 4。輸入対象をプラクティス・自動化・可視化に限定する |
| ビッグバン統合 | フェーズ末尾での一括統合により手戻りが集中する | 継続的インテグレーション＋フィーチャートグルで統合を常時分散させる |
| 二重帳簿 | 自動生成された証跡とは別に手書きの成果物を並行維持し、ドリフトする | 原則 2。生成された成果物を正とし、手書きの複製を禁止する |
| 指標の目的化 | フロー指標・カバレッジ等を個人評価やノルマに転用し、数値操作を誘発する（Goodhart の法則） | 指標はプロセス改善の診断にのみ用い、個人の評価に使用しない旨を運用ルールとして明記する |
| ゲートの形骸化 | 証跡が自動で揃うため、承認者が中身を見ずに通過させる | 👤 人間 判定項目を明確に残し、人間が判断すべき点を承認者へ具体的に提示する |
| 統制部門の置き去り | 開発側だけで証跡形式を変更し、監査・品質保証部門に受け入れられない | 証跡形式の変更は監査・QA 側の合意を得てから適用する。従来形式が求められる間は自動証跡から従来形式を生成する |

## 指標運用の統制

- フロー効率・DORA 系指標・カバレッジ・ミューテーションスコア等の指標は、プロセスとシステムの
  改善のための診断情報であり、個人・ベンダーの評価指標として使用しない
- ゲート条件として使用する指標（カバレッジ閾値等）は、その閾値の根拠と見直し手続きを明文化する
- エンジニアリング時間と統制上の待ち時間は必ず分離して報告し、統制の待ち時間を
  エンジニアリングの遅延として誤って報告しない

## 用語

| 用語 | 定義 |
|---|---|
| フェーズゲート | フェーズ間の承認関門。通過には定義された成果物と承認者の承認を要する |
| 証跡（エビデンス） | 活動の実施と結果を事後に検証可能な形で記録したもの。本方針では CI・GitHub 上の記録を一次証跡とする |
| ベースライン | 承認によって凍結された成果物の版。以後の変更は変更管理プロセスに従う |
| Living Documentation | テスト・コード等の一次情報から自動生成され、常に実態と一致するドキュメント |
| Spec-Driven Development（SDD） | 承認された仕様（要件・設計・タスク）を AI エージェントによる実装の駆動源とする開発手法 |
| Coding Agent | issue の割当等を起点に、実装からドラフト PR 作成までを自律的に行う AI エージェント。GitHub Copilot Coding Agent、Claude Code、OpenAI Codex 等 |
| EARS | Easy Approach to Requirements Syntax。構造化された自然言語で要求を記述するパターン集 |
| RTM | Requirements Traceability Matrix。要件からテスト結果までの対応表 |
| DevEx | 開発体験。フィードバックループ・認知負荷・フロー状態の 3 次元で捉える（Noda, Storey, Forsgren, Greiler, 2023） |
