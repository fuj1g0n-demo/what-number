# ユーザーストーリー品質チェック

ユーザーストーリーを精査し、すべてのチェックに合格した場合にのみ「確認済み」と判定する一連のフロー。
いずれかのチェックで問題を検出した場合は「要確認」と判定し、問題点を記録する。

タスクの管理媒体（GitHub issue またはタスクファイル）に応じて、以下を併用すること:

- GitHub issue 管理の場合: `issue-workflow` skill
- タスクファイル管理の場合: `task-file-workflow` skill

## チェックフロー

以下の手順を必ず順番通りに実行する。

### ステップ 1: 対象の確認

1. 対象がユーザーストーリーカテゴリであることを確認する（issue の場合 `user-story` ラベル）
2. ユーザーストーリーでない場合は、その旨を伝えて終了する

### ステップ 2: Acceptance Criteria チェック

1. Acceptance Criteria が明記されていることを確認する
2. **EARS（Easy Approach to Requirements Syntax）形式** で記述されていることを確認する
   - **Ubiquitous**: `<システム名> shall <要件>`
   - **Event-driven**: `When <トリガー>, <システム名> shall <応答>`
   - **State-driven**: `While <状態>, <システム名> shall <要件>`
   - **Unwanted behavior**: `If <条件>, then <システム名> shall <応答>`
   - **Optional**: `Where <特徴>, <システム名> shall <要件>`
   - **Complex**: 上記パターンの組み合わせ
3. 不備がある場合は、どの点が不足・不適切かをユーザーに説明し、修正されるまで次のステップに進まない

### ステップ 3: 設計計画

1. `docs/specs/` および `docs/design/` 配下の既存ドキュメントをすべて読み取る
2. ユーザーストーリーの内容と既存ドキュメントとの整合性を確認する
3. 判断:
   - 既存ドキュメントへの追加・変更が必要な場合: 設計カテゴリのサブタスクを作成する（変更対象ドキュメントと変更概要を記載）
   - 設計作業が不要な場合: 「設計作業は確認の上不要と判断しました。理由: <理由>」と明記する
   - 判断がつかない場合: ユーザーに質問し、必要な情報が揃うまで繰り返す

### ステップ 4: 実装計画

`incremental-planning` skill の方針に従い、実装を小さなインクリメントに分割してサブタスクを作成する。
各実装サブタスクには以下を含める:

- 実装順序（どのインクリメントの後に着手するか）
- 詳細設計の概要
- テスト計画（Unit Test / Integration Test / System Test の対象範囲。System Test のテストケースは **Gherkin 形式**）
- そのインクリメントで検証可能になる Acceptance Criteria の項目

判断がつかない場合はユーザーに質問し、必要な情報が揃うまで繰り返す。

### ステップ 5: 手動テスト計画

`manual-test-gherkin` skill を参照して手動テストの必要性を判断する。

- 自動テストでカバー可能な場合: 「手動テストは確認の上不要と判断しました。理由: <理由>」と明記する
- 手動テストが必要な場合: 手動テストカテゴリのサブタスクを作成する（テストケースは Gherkin 形式）
- 判断がつかない場合: ユーザーに質問する

### ステップ 6: 最終判定

- 全チェック合格: 下記フォーマットの構造化コメントを記録し、「確認済み」と判定する
- 問題あり: 問題点を含む構造化コメントを記録し、「要確認」と判定する

判定結果は、タスクの管理媒体に応じて以下のとおり反映する:

| 管理媒体 | 合格時 | 問題検出時 |
|---|---|---|
| GitHub issue | 「要確認」ラベルを除去し、「確認済み」ラベルを付与する | 「要確認」ラベルを付与する（「確認済み」は付与しない） |
| タスクファイル | `user-story.md` の `status` を `verified` に更新する | `status` は `not-started` のままとする |

「確認済み」ラベル（または `verified` ステータス）は、本チェックフローをすべて完遂し、
構造化コメントを証跡として記録した場合にのみ付与・更新できる。

## 構造化コメントフォーマット

```markdown
## ユーザーストーリー確認結果

### Acceptance Criteria チェック
- [x/  ] EARS 形式で記述されている
- [x/  ] 受け入れ条件が網羅的である
- 備考: <必要に応じて補足>

### 設計計画
- [x/  ] 既存ドキュメント（docs/specs/, docs/design/）との整合性を確認済み
- 結果: <「設計サブタスクを作成: xx」または「設計作業は不要と判断。理由: ...」>

### 実装計画
- [x/  ] 詳細設計・テスト計画を立案済み
- 結果: <「実装サブタスクを作成: xx, yy」>

### 手動テスト計画
- [x/  ] 手動テストの必要性を判断済み
- 結果: <「手動テストサブタスクを作成: xx」または「手動テストは不要と判断。理由: ...」>

### 最終判定
**結果**: ✅ 確認済み / ❌ 要確認
<問題がある場合は、具体的な問題点と必要なアクションを記載>
```

## 禁止事項

- 全ステップのチェックを完了する前に「確認済み」と判定してはならない
- ユーザーへの質問に対する回答を得る前に次のステップに進んではならない
- 判断に必要な情報が不足している状態で「確認済み」と判定してはならない
- `docs/specs/` および `docs/design/` 配下のドキュメントにコード例を含めてはならない
